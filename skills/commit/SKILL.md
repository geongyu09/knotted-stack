# commit 작성 커맨드

이 커맨드는 현재 워킹 디렉토리의 변경사항을 파악하여 커밋 메시지를 제안하고, 개발자의 확인을 받은 후 커밋 및 푸시를 수행합니다.

## 이 커맨드가 하는 일

1. **변경사항 확인** - 코드의 변경사항을 명확히 확인

- `git status` 명령어를 호출하여 변경된 파일 목록 확인
- `git diff` 명령어를 호출하여 unstaged 변경사항 확인
- `git diff --staged` 명령어를 호출하여 이미 staged된 변경사항 확인
- `git log -n 5 --oneline` 명령어를 호출하여 최근 커밋 메시지 스타일(컨벤션) 파악

2. **커밋 대상 및 커밋 메시지 제안** - 확인된 변경사항을 바탕으로 커밋 메시지 초안 작성

- 어떤 파일을 `git add`할지 목록으로 정리하여 제시
  - 변경사항은 최대한 작게 나누어 커밋
- 변경사항에 맞는 커밋 메시지를 아래의 형식에 맞춰 작성
  - 본문에는 **무엇을 했는지, 어떤 결정을 했는지, 그 근거와 이유**를 모두 담습니다 (아래 `커밋 메시지 형식` 참고)
  - 결정의 근거·이유는 diff가 아니라 대화·Issue·문서에서 확인하며, 확인되지 않으면 추측하지 않고 질문합니다
- **[매우 중요]** 제안 내용을 개발자에게 출력한 후 반드시 승인을 요청하고 **대기**합니다. 승인 없이는 절대로 add, commit, push를 수행하지 않습니다.

3. **커밋 및 푸시 수행** - 개발자가 승인한 경우에만 실행

- 개발자가 "네", "좋아요", "진행해주세요", "ok", "ㄱㄱㄱ" 등 긍정적인 응답을 한 경우에만 다음 단계를 진행합니다.
- 제안한 파일들을 `git add`합니다.
- 승인된 커밋 메시지를 줄바꿈 그대로 `git commit -F - <<'EOF' ... EOF` (heredoc)로 실행합니다. 여러 줄 본문이 깨지지 않도록 `-m` 한 줄 형식은 쓰지 않습니다.
  - **[매우 중요]** 커밋 메시지에 `Co-Authored-By` 트레일러나 Claude/생성 도구 관련 서명을 **절대 추가하지 않습니다.** 승인된 메시지 본문만 그대로 사용합니다.
- `git branch --show-current` 명령어로 현재 브랜치를 확인합니다.
- `git push origin <현재 브랜치>` 명령어로 현재 브랜치에 푸시합니다.
- 만약 개발자가 메시지 수정을 요청한 경우, 수정사항을 반영하여 **다시 승인을 받는 과정**을 반복합니다.

## 작동 방식

- 변경사항을 명확하고 정확하게 파악합니다.

  - `git status` 명령어로 변경 파일 목록 확인
  - `git diff` 및 `git diff --staged` 명령어로 실제 코드 변경사항 확인
  - `git log -n 5 --oneline` 명령어로 기존 커밋 컨벤션 확인

- 확인된 변경사항을 기반으로 커밋 대상 파일과 커밋 메시지를 제안합니다.

  - 기존 커밋 로그의 스타일(예: Conventional Commits, gitmoji 등)을 우선적으로 따릅니다.
  - 변경사항이 서로 다른 맥락을 포함하는 경우 개발자에게 커밋 분리 여부를 질문합니다.

- 개발자의 승인을 받은 후에만 실제 git 명령어를 실행합니다.
  - 승인 전에는 **절대로** `git add`, `git commit`, `git push`를 실행하지 않습니다.

## 커밋 메시지 형식

기존 커밋 로그의 컨벤션을 우선적으로 따르되, 확인되는 컨벤션이 없는 경우 아래의 Conventional Commits 형식을 기본값으로 사용합니다.

```
<type>: <제목>

<요약 - 무엇을 했는지>

[<결정 주제>]
<무엇을 결정했는지 + 근거 + 이유 (+ 검토한 대안)>

[<결정 주제>]
...

<트레일러 - #issue번호>
```

- **type**: `feat`, `fix`, `refactor`, `style`, `docs`, `setting`, `chore` 중 적절한 것을 선택
- **제목**: 50자 이내, 명령형 어조, 한글로 작성
- **본문**: **무조건** 작성하며, 각 줄은 72자 이내로 줄바꿈합니다. 커밋 하나만 읽어도 "무엇을 했고, 무엇을 왜 그렇게 정했는지"를 알 수 있어야 합니다. 아래 세 가지를 모두 담습니다.
  1. **무엇을 했는지 (요약)**: 제목 바로 아래 첫 문단. 바뀐 동작과 범위를 1~3문장으로 적습니다. 파일 나열이 아니라 결과(무엇이 어떻게 달라졌는지)를 씁니다.
  2. **결정 사항**: 변경 중 여러 방법이 가능했는데 하나를 고른 지점마다 `[주제]` 블록을 하나씩 둡니다. 순서, 책임 분리, 실패 처리, 이름, 저장 위치, 범위에서 뺀 것 등이 모두 결정입니다.
  3. **근거와 이유**: 각 `[주제]` 블록 안에서 결정과 함께 적습니다.
     - **근거**: 결정을 뒷받침하는 사실. 개발자 지시, Issue·PR 번호와 그 내용, 시안, 기존 코드·규칙, 서버 계약, 측정·재현 결과 등 확인 가능한 출처를 씁니다.
     - **이유**: 그 근거로부터 왜 이 방법이 나은지에 대한 판단. "~하기 위해서입니다", "~하면 ~가 생기기 때문입니다"처럼 인과가 드러나게 씁니다.
     - **대안**: 실제로 검토했거나 개발자가 제안했다가 버린 방법이 있으면 무엇이고 왜 버렸는지 함께 씁니다. 검토하지 않은 대안을 지어내지 않습니다.
- **결정 사항이 없는 커밋**: 오타, 포맷, 단순 이름 변경처럼 선택지가 없던 기계적 변경이면 `[주제]` 블록을 생략하고 요약 문단에 "왜 바꿨는지"만 한 문장 덧붙입니다.
- **트레일러**: 이슈 번호를 `#번호` 형태로 **무조건** 작성. 본문과 빈 줄 하나로 구분
  - 이슈 번호는 현재 브랜치명(e.g. `fe/feature/#189` → `#189`)에서 우선 추출하고, 브랜치명에 없으면 최근 커밋의 트레일러를 참고
  - 어디서도 이슈 번호를 찾지 못한 경우 임의로 추측하지 않고 개발자에게 질문
- **"사용자" 호칭 금지**: 커밋을 요청한 사람은 개발자이므로 메시지에서 "개발자"라고 쓰거나 주어를 생략합니다. "사용자"는 만든 앱을 쓰는 사람을 가리킬 때만 씁니다.
- **줄 앞 `#` 금지**: 본문 줄을 `#`으로 시작하지 않습니다(git이 주석으로 지울 수 있음). 주제 제목은 마크다운 헤더 대신 `[주제]`를 씁니다. 트레일러의 `#번호` 줄만 예외입니다.

### 결정·근거·이유를 모으는 방법

diff만으로는 "무엇을"은 알 수 있어도 "왜"는 알 수 없습니다. 메시지를 쓰기 전에 다음에서 결정과 근거를 모읍니다.

- 현재 대화: 개발자가 지시·선택·거부한 것, 함께 비교한 대안, 테스트·실측 결과
- 브랜치의 Issue 본문(`gh issue view <번호>`)과 ADR, 관련 PR 리뷰 코멘트
- 코드 주석과 기존 규칙 문서, 메모리에 기록된 결정

**[매우 중요]** 근거나 이유를 추측해서 채우지 않습니다. diff에는 결정이 보이는데 대화나 문서에서 이유를 확인할 수 없으면, 제안 시 해당 블록에 `(이유 확인 필요)`로 표시하고 개발자에게 질문합니다.

커밋을 작게 나눈 경우, 각 커밋 본문에는 **그 커밋의 변경에 해당하는** 결정만 담습니다.

## 개발자 확인 요청 형식

커밋을 수행하기 전, 아래의 형식으로 개발자에게 확인을 요청합니다.

```
## 커밋 대상 파일

- path/to/file1.js
- path/to/file2.js

## 제안 커밋 메시지

feat: 프로필 사진 업로드 기능 추가

S3 presigned URL로 프로필 사진을 업로드하도록 구현했습니다.

[업로드 방식]
서버를 거치지 않고 브라우저에서 S3로 바로 올리도록 presigned URL을
쓰기로 했습니다. 서버 경유 업로드도 검토했지만, 이미지가 커서 서버
대역폭과 메모리를 차지하기 때문에 제외했습니다(#12 논의).

#12

## 확인이 필요한 결정

- (없음) 또는 "[업로드 방식]의 이유를 대화에서 찾지 못했습니다. 이유를 알려주세요."

## 푸시 대상 브랜치

feature/profile-upload

---

위 내용으로 커밋 및 푸시를 진행할까요? 수정이 필요하시면 말씀해주세요.
```

## 주의사항

- **[매우 중요]** 개발자의 **명시적 승인 없이는 절대로** `git add`, `git commit`, `git push`를 실행하지 않습니다.
- **[매우 중요]** 해당 스킬은 절대로 코드를 작성하거나 수정하지 않습니다. 오직 git 관련 동작만 수행합니다.
- **[매우 중요]** 커밋 메시지에 `Co-Authored-By:` 트레일러를 포함한 어떠한 공동 작성자(co-author) 서명이나 Claude/생성 도구 관련 문구도 추가하지 않습니다. 하네스 기본값으로 co-author가 붙도록 설정되어 있더라도, 이 스킬에서는 해당 트레일러를 제외하고 커밋합니다. 이슈 번호 트레일러(`#번호`)는 **무조건 포함**합니다.
- 이미 staged된 파일이 있다면, 해당 내역을 개발자에게 먼저 보여주고 그대로 포함할지 질문합니다.
- 현재 브랜치가 `main`, `master`, `develop`, `dev` 등 보호 브랜치로 추정되는 경우, 푸시 전에 **반드시** 개발자에게 재확인을 받습니다.
- 원격 브랜치가 아직 존재하지 않는 경우 `git push -u origin <현재 브랜치>` 형태로 upstream을 설정하며 푸시합니다.
- push 과정에서 충돌이나 rejected 오류가 발생한 경우, 임의로 `--force` 옵션을 사용하지 않고 개발자에게 상황을 보고한 뒤 지시를 기다립니다.
