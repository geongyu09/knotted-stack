# knot-mode

플레이북과 원칙 파일은 이 파일과 같은 폴더의 `playbooks/`, `principles/`에 있으며, 필요한 파일만 골라서 읽습니다.

## 시작할 때

1. 첫 응답에서 사용자의 목표와 목표를 채우는 가장 작은 변경을 한두 문장으로 다시 말합니다.
2. 아래 표에서 플레이북 하나를 골라 전부 읽고, 단계를 todo 목록에 그대로 적습니다. 건너뛰는 단계에는 `skip: 이유`를 적습니다.
3. 맞는 플레이북이 없으면 "재현 또는 현재 상태 확인 → 가장 작은 변경 → 검증" 순서로 직접 계획을 세웁니다.

## 개발 기본 규칙

코드를 쓰거나 고치는 작업이면 플레이북을 고르기 전에 `ponytail.md`를 전부 읽고 따릅니다. 프로젝트마다 다른 규칙(프레임워크, 테스트 명령, 폴더 구성, 코드 스타일)은 프로젝트의 CLAUDE.md와 AGENTS.md에서 읽으며, 프로젝트 규칙과 `ponytail.md`가 부딪히면 프로젝트 규칙을 따릅니다.

## 플레이북

| 작업 | 파일 |
| --- | --- |
| 버그 수정 | `playbooks/bug-fix.md` |
| 기능 추가 | `playbooks/feature.md` |
| 리팩터링 | `playbooks/refactoring.md` |

## 조건에 따라 할 일

| 조건 | 할 일 |
| --- | --- |
| 함수 경계를 넘는 변경 | 코드를 쓰기 전에 타입과 시그니처부터 적고 사용자에게 보여 줍니다. |
| 서로 독립인 조각이 둘 이상 | `delegate` 스킬의 나누기(swarm) 방식으로 맡깁니다. |
| 설계 후보가 둘 이상이고 실행해 보면 결론이 나는 경우 | `delegate` 스킬의 겨루기(arena) 방식으로 맡깁니다. |
| 보안, 데이터 정합성, 되돌리기 어려운 변경 | `delegate` 스킬의 따지기(interrogate) 방식으로 리뷰를 맡깁니다. |
| 출력이나 파일이 길어서 컨텍스트를 많이 쓰는 조사 | 조사를 에이전트에게 맡기고 요약만 받습니다. |
| 되돌릴 수 있는 선택 | 사용자에게 묻지 않고 고른 뒤, 무엇을 왜 골랐는지 보고합니다. |
| 배포, 데이터 삭제, 공유 브랜치 force-push, 외부로 나가는 메시지 | 멈추고 사용자에게 확인을 받습니다. |

## 원칙

원칙을 적용할 때는 해당 파일을 전부 읽고, 최종 보고에 어떤 원칙이 어떤 선택을 바꿨는지 적습니다. 읽지 않은 원칙은 인용하지 않습니다.

| 원칙 | 적용할 때 | 파일 |
| --- | --- | --- |
| 원인을 고치기 | 디버깅할 때 | `principles/fix-root-causes.md` |
| 실제로 되는지 증명하기 | 작업을 끝냈다고 말하기 전 | `principles/prove-it-works.md` |
| 컨텍스트 아끼기 | 큰 출력, 긴 파일, 반복해서 읽기가 예상될 때 | `principles/guard-the-context-window.md` |

## 끝낼 때

최종 보고는 목표, 바꾼 내용, 검증 증거(실행한 명령과 결과), 확인하지 못한 부분의 순서로 짧게 씁니다.
